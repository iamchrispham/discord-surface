# Spark sidecar possibilities

Research completed September 5, 2026, Pacific time. Five internal lenses plus an independent ChatGPT 6 Pro read, followed by a tier/acknowledgment reframe and a conductor-context correction in the same chat. The current recommendation below incorporates all operator steering. These features are not enabled.

## Claim

The primary objective is fewer status-only conductor turns and less persistent-context growth. Routine snapshots and sidecar interpretation happen outside the conductor session. Spark earns its additional role only if it improves useful meaning beyond a deterministic snapshot, after accounting for corrections and escalations. Spare subscription capacity alone is not a reason to add a model call.

## Decision At Stake

Choose a snapshot baseline, an optional Spark association preview and a separate Luna low-versus-medium check for harder cases. The conductor remains the channel's recipient and task owner, while routine publication follows its standing policy without a conductor review turn per digest. No production posting, polling reader, new conductor, terminal control or authority change was performed during this research.

## Possibilities

### O1 Question follow-through

Connect an explicit earlier operator question to newly arrived evidence, with original excerpts attached.

Example: “You asked whether both cold and warm starts were checked. The new result covers warm starts. Cold starts remain unestablished in this packet.”

Input: the question, relevant current scope, latest conductor answer and a few new receipts. Trigger: a relevant worker result. Output stays in the sidecar publishing path as a labeled association, not a resolved-question mutation or a required conductor review. Original input and required replies remain independent.

Potential value: semantic matching across differently worded questions and results. Main risk: confusing related evidence with a complete answer. First proof: compare the matched evidence with existing conductor answers and a deterministic question/receipt view.

### O2 A meaningful catch-up

Explain what changed relative to an identified earlier snapshot, preserving unchanged but important waits.

Example: “Since the previous update: the selected fix is unchanged, local checks now pass, and device verification is still outstanding. The next recorded step is reviewing that device result.”

Input: previous digest, current board, bounded intervening evidence and explicitly stated intent. An event can prepare a preview without automatically posting a message. Say “since the previous update,” not “since you last read this.” Delivery is not proof of attention.

Potential value: less rereading when returning to a channel. Main risk: duplicating `/cs` or inventing an explanation for a plan change. Test against `/cs` plus the conductor's existing final messages, not against a deliberately poor raw-log baseline.

### O3 Decision breadcrumbs

Help the conductor answer “Where did we decide that?” with the actual source and current scope.

Example: “Automatic retry was disabled in this decision. That states policy, not whether a retry occurred.”

Input: explicit decision excerpts and existing supersession metadata. Output: candidate references and search aliases. No new authoritative memory, inferred motives or automatic durable-state edits.

Potential value: recovering decisions phrased differently from the later question. Main risk: retrieving a superseded decision or the wrong goal. Compare with ordinary keyword search before adding an index.

### O4 Steering-message comparison

Prepare a small comparison when the operator changes part of an assignment.

Example: “Changed: pause device runs. Unchanged: do not merge. Unresolved: how the outstanding device-proof requirement will be satisfied.”

The original message reaches the conductor unchanged and immediately. Spark's interpretation does not alter scope, interrupt work or delay delivery.

Potential value: catching a missed negation or preserving constraints across voice-dictated corrections. Main risk: interpreting an ambiguous reference or question as an instruction. Test only as a private companion to the originals.

### O5 An already-needed decision brief

Assemble the conductor's explicit question, existing options and recorded consequences into a compact packet.

Spark does not decide that the operator needs to be asked. It cannot turn a technical uncertainty into a human decision or invent deadlines and alternatives.

Potential value: fewer clarification exchanges when evidence is scattered. Main risk: paying twice for a question the conductor could already express clearly. Compare against a template containing the original question and options.

### O6 A private consistency hint

Point the conductor to a possible discrepancy between a report and its support, limited to known failure classes such as owner, scope, timing and policy versus event.

Example: “The report says finished. This packet contains unit-test proof, while the stated acceptance also asks for device proof.”

This is a candidate for inspection, never a verdict, publication gate, automatic alert or new review loop. Missing evidence in a bounded packet does not establish that evidence is absent everywhere. No hint means only that no hint was produced.

The operator accepts this role with an escalation tier. Spark may nominate a discrepancy anchored in the existing owed-item view or explicit conductor context. A single Luna low or medium check gets the underlying excerpts, not just Spark's interpretation. A material warning may then be surfaced under the conductor's standing policy. Routine uncertainty is not a new obligation, publication gate or automatic conductor wake.

## Agreements

Both reads favor explicit source context, a fair no-model baseline and a sidecar without execution authority. Neither supports a narrator after every native turn, invented rationale, model-controlled alert suppression, or a draft/grade/rewrite chain presented as independent verification. A source pointer proves that an excerpt exists, not that it supports Spark's interpretation.

## Disagreements

The original local recommendation held warnings for later, while Pro ranked a private warning second. The operator resolved that design preference: warnings are valid when tiered and anchored in the existing `/cs` owed items. The revised design permits a bounded Luna check, not another warning or review loop.

The original framing also contemplated conductor review of sidecar proposals. The operator's explicit goal of preserving conductor context rules out per-digest review. Pro changed its recommendation accordingly: publishing-policy ownership does not require per-message conductor inference.

Question matching remains useful, but not every important development answers an explicit question. Existing mandatory updates and conductor responsibilities must not be suppressed by a sidecar's relevance verdict.

## Biggest Correction

Move routine status reporting outside the persistent conductor first. A model-free publisher of existing artifacts can already avoid status-only conductor turns. Spark's added value is connecting those artifacts to stated questions, goals and decisions. Do not credit all context savings to the model.

Replacing status requests with automatic summaries that are then reingested into the conductor defeats the objective. Routine summaries must stay out of its input, including replay and backfill. At the inspected head, `src/state.js:1207` rejects bot-source input, but end-to-end isolation of a future sidecar publication path remains to be tested.

## Decision

Use the following proposed responsibility split:

- T0 Ordinary code: collect bounded existing artifacts, preserve facts, render basic changes, apply standing publication rules, and display delivery acknowledgments. Do not invoke `/cs` in the conductor or ask it for a new report.
- T1 Spark: add an association between a recorded owed item or earlier question and new evidence, or prepare a concise catch-up using already-stated intent. No separate channel identity or direct response to incoming user messages.
- T2 Luna low or medium: one bounded check for a predefined consequential scope distinction, competing claims or a harder interpretation. These are alternative experimental settings. No measured quality/cost/latency ladder is established. Do not escalate by model self-confidence or serially retry low, medium and high.
- T3 Conductor: own questions, decisions and execution. Routine sidecar summaries do not create a conductor turn. Only a policy-qualified material decision, unresolved question or meaningful warning enters its session.

Use existing `/cs` sources for owed items. Do not make a second obligation database or let models create or clear owed items. Preserve direction: what the operator owes and what the conductor owes the operator are different facts.

Acknowledgments are a separate, model-free improvement. Proposed signals are an inbox reaction for durable save and eyes for a real native acknowledgment. Neither means successful completion. The current `src/discord.js:130-174` sends a textual receipt. Native queue success in `src/native.js:198-209`, or Claude endpoint 202, establishes submission rather than recognition. A true acknowledgment needs an exact owner event tied to the original message and binding generation. That event is not verified in the current adapter. Missing eyes means recognition unverified, not ignored.

Discord documents message-level reactions in its [Message Resource](https://docs.discord.com/developers/resources/message#create-reaction). This supports the display mechanism, not the proposed native acknowledgment semantics. Reaction failure must not rewrite a successful durable save. Replacing routine receipt text with reactions can reduce noise independently of Spark.

## Reframed Internal Panel

- Hard skeptic: REINFORCE the model-free snapshot baseline. It directly targets status-only conductor turns, so the model must demonstrate added value over it.
- Empiricist: PARTIAL on context savings. Offline previews can establish answerability and modeled savings. They cannot prove which future operator requests were actually avoided.
- Mechanism designer: REINFORCE artifact collection and publication outside native conductor inference. Preserve message attribution, generation, bot-input exclusion and exact acknowledgment evidence.
- Economics critic: PARTIAL on the Luna tier. Compare low and medium on the same source packets and report actual wall time and context use. Do not turn the user's cheap/slow characterization into measured economics.
- Metric critic: REBUT counting fewer `/cs` calls alone. Subtract extra warning turns, corrections, repeated snapshots and reinjected summaries. Track understanding and unresolved work as well as context use.

## Next Proof Step

Run two local preview arms on a small fixed set of real historical activity windows:

A. A bounded deterministic snapshot of existing `/cs` artifacts and already-written conductor context, without invoking the conductor.

B. The identical snapshot plus an optional Spark question/owed-item association.

Use only information available at that point, with no later resolution leaked into the packet. Initially prefer source-span selection and an advisory relation over invented narrative. Grade against source-anchored judgments prepared before seeing the model output. Include partial answers, irrelevant receipts and ambiguous evidence. Sample ordinary windows as well as interesting ones to measure whether useful opportunities occur often enough.

On a prespecified subset of consequential discrepancies, compare one Luna-low check with one Luna-medium check as alternatives. Give each the actual packet. Include some unflagged controls so only examining Spark's candidates does not hide missed warnings. High effort and serial retry ladders are outside the first comparison.

The primary metric is net conductor turns, input tokens and retained-context growth avoided, subtracting escalations, corrections and summary reinjection. Also measure reader comprehension, latency, source-checking effort, false/missed warnings and recurring preparation work. Twelve windows is a screening suggestion, not a reliability sample. Pro's earlier three-additions and 20% thresholds remain advisory and are not adopted as product gates.

Separately mock the saved/acknowledged display using the same event traces. Do not mark a real agent acknowledgment as tested until an exact native event exists. Do not attribute model-free noise reduction to Spark or Luna.

No prototype was launched by this research. A later usage trial is required to measure actual avoided conductor turns.

Faithful interpretation on real work, actual conductor-context savings, useful opportunity frequency, Luna low/medium performance, native acknowledgment semantics, sidecar replay isolation, automatic publication and reliability across changing conductor state remain unproven.
